# Arshite Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a tested Deno Deploy GitHub App named Arshite that creates upstream-sync PRs and provides conservative, opt-in PR automation.

**Architecture:** One Deno TypeScript service verifies GitHub webhooks, registers installations in Deno KV, and processes repositories from webhooks and one cron job. Octokit performs installation-scoped GitHub API operations; GitHub remains authoritative for PR and branch state.

**Tech Stack:** Deno 2.9+, TypeScript, Deno KV, Deno cron, Octokit, Zod, Deno test.

**Spec:** `docs/superpowers/specs/2026-10-31-arshite-design.md`

## Global Constraints

- Auto-merge and hard reset both require `autoMerge: true`; the default is `false`.
- Read `.github/pull.yml` and reject unknown keys.
- Use no MongoDB, Redis, dashboard, or unauthenticated processing endpoint.
- Never log credentials, tokens, webhook secrets, or config contents.
- Verify webhook HMAC-SHA256 signatures before JSON parsing.
- Run `deno fmt --check`, `deno lint`, `deno check`, and `deno test` before completion.
- The workspace is not a Git repository; do not initialize Git or create commits unless the user separately requests them.

## File Map

- `deno.json`: dependencies and development tasks.
- `src/types.ts`: shared repository, rule, and GitHub client interfaces.
- `src/env.ts`: environment parsing and private-key normalization.
- `src/rules.ts`: strict YAML config parsing.
- `src/registry.ts`: Deno KV installation/repository records, delivery IDs, and leases.
- `src/webhooks.ts`: signature verification and typed webhook event parsing.
- `src/merge.ts`: pure merge-eligibility decision.
- `src/processor.ts`: branch comparison, PR synchronization, automation, merge, and hard reset.
- `src/github.ts`: GitHub App and repository-processing composition.
- `src/main.ts`: HTTP routes, event dispatch, and cron.
- `tests/*_test.ts`: focused unit and integration tests.
- `.env.example`, `.gitignore`, `README.md`: configuration and deployment instructions.

- [ ] **Step 1: Write failing mocked-GitHub tests**

Build a route-aware mock client. Cover:

1. `ahead_by: 0` performs no mutation.
2. An existing matching PR is reused.
3. A missing PR is created with the expected title, head, and base.
4. Labels and only missing assignees/reviewers are applied.
5. Conflicts add the conflict label/reviewers; a later clean PR removes only the conflict label.
6. A clean opted-in PR is reread and merged with the configured method.
7. A hard reset requires both opt-in and `hardreset`, then patches the base ref with the compare response's `head_sha` and creates no PR.
8. A missing config produces no API mutation; invalid config propagates a useful rule error.

Expected: FAIL because the processor is missing.

- [ ] **Step 3: Implement the processor**

Use these GitHub routes:

- `GET /repos/{owner}/{repo}/contents/{path}` with the default-branch ref and `.github/<configFilename>` path; decode the base64 content before calling `parseRules`.
- `GET /repos/{owner}/{repo}/compare/{basehead}` with `basehead: "<base>...<upstreamOwner>:<upstreamBranch>"`.
- `GET /repos/{owner}/{repo}/pulls` filtered by `state`, `head`, and `base`.
- `POST /repos/{owner}/{repo}/pulls`.
- `GET /repos/{owner}/{repo}/pulls/{pull_number}` immediately before automation decisions and merging.
- Issue label/assignee routes and PR reviewer/merge routes.
- `PATCH /repos/{owner}/{repo}/git/refs/heads/{ref}` only for the explicit hard-reset path.

Keep labels idempotent, filter requested reviewers, ignore only 404 when removing a stale conflict label, and never retry a non-idempotent mutation in a manual loop.
